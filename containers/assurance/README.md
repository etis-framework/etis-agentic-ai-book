# Supply-chain assessment and release authority

This is the first, strict enforcement stage of Patch B. The historical assessment register is populated from the four November 27 CI JSON reports (220 high-severity package/image findings, 15 distinct CVEs). Every record is **under investigation**. The historical image ID is provenance, not authority to apply a disposition to a rebuilt image. The empty risk register explicitly grants no exceptions.

The Linux scanner wrapper retains unfiltered reports, inventories, SBOMs, hardening observations and its existing independent HIGH/CRITICAL exit gate. The host evaluator reconciles exact image identity, architecture and Debian inventory across the evidence files, hashes the inputs, records all severities and matches review work items by CVE/package/version/architecture/role. Missing or inconsistent evidence, unsupported schema, hardening failure and any HIGH/CRITICAL finding block acceptance. A scanner failure remains blocking independently of the evaluator. Evidence hashes support later integrity checks; they are not signatures or independent attestation. A clean report does not prove security.

Run the standard-library tests with `python3 -B containers/assurance/test_security_gate.py`. The evaluator is host-side only; do not install additional software in the educational images. CI retains its generated disposition JSON with the raw artifacts even on failure. The existing scheduled CI runs the same gate. Review UNKNOWN, known-exploited and actionable lower-severity findings separately; this automatic severity gate is not the entire release decision.

## Approval boundary (not enabled)

Do not add an ignore file or reinterpret the draft register as approved VEX. A subsequent reviewed change must establish independent maintainer authorization, exact image and package binding, positive applicability evidence, expiry and revocation, and enforcement of a trusted policy outside the candidate's control. Critical findings remain non-waivable. Fixable high findings must be remediated. An affected but accepted risk is not a VEX not-affected statement. No OpenVEX document is issued until affirmative product-specific dispositions are reviewed; do not publish speculative claims. Rebuilds or dependency changes require renewed evidence. The current evaluator deliberately rejects any populated risk register and any non-draft assessment status, including purportedly approved or expired records.

This is bounded educational supply-chain governance, not production certification. It does not authenticate arbitrary report files supplied outside the trusted scanner workflow, establish reachability, or verify the upstream scanner publisher checksum independently.

## Patch C — applicability observations (review only)

The scanner executes `probe_applicability.py` via standard input in the exact locally inspected image, with no source bind mount, network, elevated capabilities, or writable root. It records process identity, capability sets, Seccomp/no-new-privileges, SQLite compile options, OpenSSL version, standard service and CLI locations, Perl default module search paths, curl capabilities and fstab entries. The evaluator requires the JSON evidence, validates its scope and shape, and hashes it with other inputs. This establishes observations of the selected runtime, not cryptographic attestation or all possible reader configurations. Failed probes block acceptance. The IDE network overlay and reader-added files are outside this probe's scope.

The register now contains CVE-specific review rationales and advisory links, reviewed 2026-11-27. Three narrow review hints identify absence at standard locations or default module resolution for systemd-homed, Archive::Tar and verification-only infocmp. They do not prove global absence, cover historical layers, or grant VEX status. A present component, unexpected package or unregistered finding receives no absence hint. Both gates still block every HIGH/CRITICAL finding. The raw report is unchanged. No risk acceptance, expiry policy activation or VEX publication is authorized. A maintainer must decide whether to adopt a separately reviewed policy allowing bounded acceptance for otherwise unfixable findings; until then release remains blocked.

## Patch D — approved policy, protected decision implementation

The maintainer approved the governed vulnerability policy on 2026-11-27, not any individual vulnerability. Critical findings are non-waivable; reported or independently confirmed supported fixes for high findings require remediation. An affected high finding without a supported fix may receive a time-bounded approval (at most 30 days); a reviewed absence claim is not an affected-risk acceptance. Unknown, changed, revoked, expired or unassessed findings block. Keep the entire original scan, including lower severity findings. Review those separately. No production certification is implied.

`authorize_release.py` implements a separate decision entry point for a **protected release operator**, not a candidate-controlled GitHub Actions exception switch. Ordinary CI still runs both strict gates and cannot invoke an exception through the assessment register. CI runs both test suites. Deployment of a protected policy and evidence environment, and the required-check transition, must be independently approved before governed PASS may authorize release. Until that deployment is verified, the strict CI gate remains mandatory. Do not bypass branch protection, replace a failed required check with a manual claim, or upload private keys to GitHub.

### Operator trust boundary and procedure

1. Independently review and pin the evaluator, scanner, probe and policy at a trusted revision outside the candidate checkout. Run scanning/building on an isolated worker, with no signing secrets, protected authority files or writable trusted policy mounts. The trusted scanner must complete its full JSON and SBOM commands successfully. Do not treat a scanner crash, partial artifact, or candidate-supplied report as evidence. Preserve artifact custody and bind the exact source commit and both image roles/architectures. Review raw scanner failures: only genuine findings are eligible for governed disposition, not execution errors. The signing and decision host must not execute candidate code or candidate scripts. Transfer complete evidence into operator-controlled, immutable/read-only storage. Verify the scanner publisher checksum separately.
2. On the protected operator host, maintain an external directory containing independently provisioned `reviewer.pem` and `maintainer.pem` public keys, `revocations.json`, `review-notes/`, and the signed authorization for one specific image scan. Protect the directory, public keys, revocation register, trusted evaluator, system clock and execution environment against candidate changes. Separate identities and private keys are mandatory; distinct keys alone do not prove distinct people. Sign using private keys kept outside the candidate and scan worker. No real keys or approvals are checked into this repository.
3. Review each finding against current Debian and upstream advisories, including supported backports. Capture the actual advisory evidence and review reasoning in a text review note, including any fix availability, affected code/path, controls, scope and remaining risks. Name it `review-notes/<SHA256>.txt`. For `not_affected`, the independent review must affirm that vulnerable code is absent in the exact runtime, not merely unused or absent from one standard location. The narrow automated absence hint is a necessary extra check, not sufficient proof. Otherwise use `risk_accepted` only if explicitly authorized. The signed review must be after the scan and no more than 24 hours old at evaluation. Scanner-reported fixes always block, even if an approval claims otherwise. Automatic publisher advisory reconciliation beyond the scanner database is not implemented: independent fresh review is mandatory and must not be replaced by a Boolean guessed from the scan.
4. Construct `authorization.json` with exactly these fields: `schema_version: 1`, unique `authorization_id`, `candidate_commit` (40 lowercase hexadecimal characters), `role`, `architecture`, `image_id`, `evidence_sha256` (copy the full map from the independently generated strict disposition), `issued_at` and `expires_at` (UTC ISO timestamps ending in Z), and `decisions` (list). Each decision has `finding_sha256` (computed using `finding_fingerprint` from the trusted evaluator on the strict finding), `disposition` (`not_affected` or `risk_accepted`), substantive `rationale`, `advisory` (exact Debian tracker CVE URL), `supported_fix` (must be explicitly false), `reviewed_at` (UTC), `review_note_sha256`, and `absence_confirmed` (true only for a verified absence determination). Bind each decision to the full scan/evidence map, not a mutable tag. The fresh scan and review requirement means new scan evidence requires a new decision even within the 30-day ceiling. This intentionally favors safety over approval reuse.
5. Each independent authority reviews the exact bytes and signs the same document using OpenSSL SHA-256 detached signatures. Example commands on their respective trusted signing hosts (paths illustrative, never use test keys):

   ```sh
   openssl dgst -sha256 -sign /protected/reviewer.key -out authorization.json.reviewer.sig authorization.json
   openssl dgst -sha256 -sign /protected/maintainer.key -out authorization.json.maintainer.sig authorization.json
   ```

   Set `revocations.json` to `{"schema_version":1,"revoked_authorization_ids":[]}` only when the protected authority has actually established that no authorization has been revoked. Keep it current; adding an ID invalidates that authorization. The evaluator does not independently obtain revocation state from an external service: custody and freshness of this file are operational controls. A missing file is an error.
6. Run on the protected decision host using the pinned, independently reviewed evaluator, trusted evidence, external authority directory and a new output directory:

   ```sh
   python3 -B /trusted/policy/containers/assurance/authorize_release.py \
     /protected/evidence companion amd64 sha256:IMAGE_CONFIG_DIGEST CANDIDATE_COMMIT \
     --authority-dir /protected/authority --output-dir /protected/new-decision
   ```

   Replace illustrative digests and paths with actual verified values. This per-image command is for diagnostics; use the aggregate command below for the security acceptance decision. The output preserves findings, scope, evidence hashes, signer fingerprints and authorization digest. A signed decision applies only to the specific evidence; changing an image, finding, version, role, architecture, commit or evidence hash invalidates it. A generated OpenVEX candidate uses the exact image config identity, and is emitted only for CVEs whose every reported record in that image is approved `not_affected` and whose complete governed gate passes. An affected-risk acceptance never generates a not-affected claim. Independently validate the generated OpenVEX against the official schema and review its product identifiers before publication; no OpenVEX is published by this patch. Retain the signed authorization, review notes, raw evidence and governed result under protected custody. Do not imply the digest identifies an OCI manifest.

7. Before deployment, establish a trusted required release check outside candidate workflow control (for example a separately protected release-control repository/runner), confirm it uses an immutable approved policy revision and trusted evidence collection, and test that candidate modifications cannot grant approval or replace its result. Require all four governed decisions, native and container functional gates, manual host acceptance, and final maintainer release authorization. Until this external boundary exists, do not change the strict required CI gate. Weekly CI continues to flag findings; a fresh protected assessment is required before any release. This patch does not configure GitHub settings or establish an independently administered service.

Tests: `python3 -B containers/assurance/test_authorize_release.py` uses temporary RSA test keys; these are generated only in a temporary directory and removed. No production signing credentials are involved.

## Integrated four-scope decision (Patch E)

The protected operator must establish a fresh immutable evidence set for one exact candidate commit. Use `aggregate_release.py` from the reviewed, pinned policy checkout on the protected decision host, not from an untrusted candidate checkout. The operator-controlled root must contain `manifest.json` with exactly `candidate_commit` and `images`; `images` is an array of four objects with exactly `role`, `architecture`, and `image_id` (the inspected image config digest). Require one companion and one dev image for each of amd64 and arm64. The root contains `evidence/amd64/` and `evidence/arm64/` with all six scanner evidence files per role, and `authority/<role>-<architecture>/` with the signed per-image document, review notes, trusted public keys and current revocation register described above. Use a new output directory under protected custody. Example (illustrative paths):

```sh
python3 -B /trusted/policy/containers/assurance/aggregate_release.py /protected/release-input /protected/new-output
```

The command executes each trusted per-image evaluator itself; it never consumes submitted PASS files. Missing, duplicate, failed, expired, differently scoped or differently signed decisions block. All four must bind the same candidate commit, distinct image identities, distinct authorization IDs and the same independent reviewer/maintainer key pair. `aggregate-security.json` records the outcome and retains per-image results. PASS is container-security-only, not release authorization. A partial run cannot pass. Protect the manifest, evidence, outputs, trust inputs and revocation state from modification throughout the decision. The evaluator parses and hashes the same in-memory evidence bytes; the scan timestamp is taken from those bytes. This does not establish independent evidence custody by itself.

Generated VEX candidates are named `vex.UNVALIDATED.json`. Do not publish or feed them into scanners until the official OpenVEX schema and product identities are independently validated. Automatic upstream advisory reconciliation and protected required-check deployment are not implemented. Fresh human review and exact scan binding remain mandatory; no approval reuse has been enabled. The 24-hour freshness restriction and 30-day maximum acceptance are unchanged. No actual vulnerability approval or policy relaxation is included. Candidate CI still enforces the original unconditional gates. Run `python3 -B containers/assurance/test_aggregate_release.py` alongside the existing suites.
