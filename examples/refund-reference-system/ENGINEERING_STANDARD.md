# Companion engineering standard — Builds 0–5

This is the **normative review checklist for the book's teaching code**. It does not claim that the code is certified for real payments. Implementers must preserve ETIS reference architecture, the nine logical enterprise responsibilities (E1–E9) and cross-domain contracts (C01–C09), defined in Chapter 8; *physical modules are not themselves security boundaries*. Prefer simple, typed, inspectable code over framework-specific abstractions without learning value.

## Mandatory requirements for every build

1. **Authority is explicit.** E3/C04 produces untrusted advisory data. It may never call E6 payment facilities, mint RF-1042, or alter E7 authoritative operation state. Only a trusted-execution (E5) path with independently checked case-specific authority may cause a consequential command; Build 3 demonstrates request-path enforcement, not protected same-user OS isolation. A token proving agent identity is **not** transaction-specific business authorization. The local Build 0 function API is not a protected boundary. In Build 3, even an educational single-worker E5 process must bound the **entire framing time**, validate message sizes, and contain caller disconnects without terminating the service. A missing post-effect reply is UNKNOWN to the caller, never permission for a blind retry. These controls do not substitute for production concurrency, backpressure or hostile same-UID isolation.
2. **Contracts precede implementation.** Define input/output types, scope and provenance, validation, error categories, idempotency semantics, preconditions/postconditions, and ownership before adding a new capability. State which ETIS reference architecture logical contract is represented and which contract obligations are absent.
3. **Money is exact and bounded.** Use integer minor units or an explicit decimal currency type with verified precision. Reject booleans, floats, negative amounts, invalid identity/scope and inconsistent requests at the trusted boundary. No user or model text is a policy source.
4. **State is recoverable.** Durable operational state (E7) owns local workflow/operation knowledge; the business-system responsibility (E8) owns authoritative truth (represented by a simulated provider in Builds 0–5). Preserve stable operation ID, immutable intent, durable status, and source observation. A timeout, crash, lost acknowledgment or inconclusive lookup never becomes FAILED or permission to invent a new operation. Do not silently retry uncertain consequential requests.
5. **Concurrency has a declared boundary.** Use atomic local claims / uniqueness in a one-process fixture. For high-risk multi-worker operation, require durable coordinator ownership, lease/epoch fencing, E5 enforcement against stale owners, and provider contract assurance. Never suggest SQLite's atomic claim is equivalent to distributed fencing.
6. **Errors are deliberate.** Distinguish policy denial, invalid request, unavailable dependency, inconsistent provider response, and infrastructure failure. Keep diagnostic details safe for logs; do not leak credentials/PII. An infrastructure error after E7 dispatch is an UNKNOWN *operational outcome* even if the simulator does not yet persist a separate UNKNOWN state.
7. **Operational evidence is independent.** Report correlation/operation ID, structured decision records, provider observation provenance, policy version, actor/approval scope, timing, and reviewer actions at the appropriate production build. Do not manufacture evidence from model explanations. Build 0's CLI JSON is *not* an audit log or telemetry pipeline.
8. **Tests prove negative boundaries.** Add authorization denial, cross-tenant, compromised-agent, schema rejection, duplicate and concurrent dispatch, lost acknowledgment, provider absence/conflict, restart/reconciliation, failure injection, and operator containment when applicable. Tests must be deterministic, self-contained, and specify what they do not prove.
9. **Keep the teaching path executable.** Include a root README, build README, architecture map, testing/evidence matrix, prerequisites, exact commands, expected outcomes, safe cleanup, debugging hints, and a concise next-build delta. Tests, prose, figures and terminology change together.
10. **Publish reproducibly.** Python versions/dependencies must be documented and pinned when introduced; no live credentials in the repo; fail CI on static and dynamic checks. Every edition points to an immutable tag, not mutable `main`. Follow all chapter-level manuscript, figure, citation and page-budget QA gates.

## File and code review rubric

For each change, reviewers inspect public API clarity, modular cohesion, naming/types, resource cleanup, transaction and race behavior, exceptions and CLI/API outcomes, state reconstruction, security scope, test design, documentation accuracy, and relative line-by-line agreement with the chapter. A `TODO` is acceptable only when it identifies **the missing mechanism, the owner/boundary, the consequence of omission, the chapter introducing it, and verification evidence**; it must not masquerade as an implemented control. A stub that would allow an unsafe effect by default is prohibited.

## Reviewer exercise

For each build ask: *Can I execute the exercise from a fresh clone? Can I identify who can authorize a refund? Can I reproduce a denied action and an unresolved outcome? Can I distinguish mock E8 truth from E7 local belief? Can I see what the next build adds without interpreting a model-generated explanation as proof?*

## Mandatory source architecture diagram for all builds (approved series-wide rule)

Every build directory must version-control `architecture.svg` and embed it by relative link in its README. The SVG must map actual modules, interfaces and storage to applicable ETIS reference architecture responsibilities/contracts; distinguish software/module boundaries from independently enforced authority and OS isolation; identify omitted production controls; and be kept in sync with the implementation and tests. Inspect source geometry, rendered readability and GitHub-relative link existence. No build is complete without this diagram.


## Mandatory Build 4 and future provider-adapter standard

Provider-facing examples must make interface version, idempotency key/scope/retention, amount units, typed status evidence, the distinction between local dispatch and external truth, and no-blind-retry semantics observable in source and negative tests. Every SQLite connection has explicit close semantics; simulate lost acknowledgments after an effect, absent status evidence and conflicting provider records. Reconciliation must never create intent or dispatch. A provider simulator cannot claim commercial provider guarantees. Every new build directory must contain a checked-in `architecture.svg` embedded in its README and must identify actual Python modules, logical E-domain/C-contract mappings, authentic enforcement boundaries, and deliberately omitted production mechanisms with owners and verification requirements. Diagram and README are part of the same code-review/QA patch as the source.


## Build 5 coordination standard (Chapter 27)

Every optional E2 coordinator must explicitly name the authoritative ownership store, lease/epoch fencing enforcement point, timeout/clock assumptions, one-time first-effect intent and crash-recovery semantics. Protect against stale **state mutations** and independently prove whether consequential execution also enforces ownership; never conflate them. Reconciliation must never reissue RF-1042. Each future build directory must contain a reviewed, checked-in source-module `architecture.svg` embedded in its README and synchronized with code/tests. Missing real multi-host consensus, OS isolation, finance approval and production telemetry must be individually documented with owners and proposed evidence.
