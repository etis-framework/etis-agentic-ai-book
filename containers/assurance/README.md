# Supply-chain assessment and maintainer acceptance

The ETIS maintainer approved a revised, single-maintainer policy on November 27, 2026. It supersedes the earlier proposed dual-signature and external release-operator workflow. No external reviewer or signing keys are required. This is ordinary repository-maintainer governance, not independent attestation or an independently protected gate. Only the maintainer may approve policy/register changes; inspect the exact candidate diff and CI evidence before merging or tagging. A candidate-controlled workflow cannot prove its own integrity.

## Active security gate

`scan-images.sh` scans both exact image roles on each Linux architecture. It retains the original all-severity JSON, SBOM, package inventory, runtime hardening and applicability evidence, raw HIGH/CRITICAL output and raw exit status. A scanner error blocks. Exit 42 is reserved for reported HIGH/CRITICAL findings; the evidence evaluator must decide whether every such finding is covered by a valid disposition. CI requires both architecture jobs and all native jobs. Neither a clean scan nor an accepted finding proves security.

`evaluate_security_gate.py` reconciles scanner, SBOM, package inventory and runtime probe identities, hashes the original evidence, and applies exact scope matching. Critical findings and high findings with a reported fix cannot be waived. New or changed high findings (role, architecture, CVE, package, installed version, scanner status, severity, reported fix or required applicability observation), invalid evidence, failed hardening and expired or missing decisions block. The draft assessment register is not approval. The separate `risk-acceptances.json` is the maintainer-approved decision register, with a maximum 30-day validity. Removing a decision revokes it. There is no automatic renewal and no blanket CVE suppression. A known supported fix always requires remediation, even if the scanner has not yet learned of it.

Basis: GitHub Actions [run 23](https://github.com/etis-framework/etis-agentic-ai-book/actions/runs/46039665589), commit `5922e3f78d7be7cd966788838d489629b7193847`. Both architectures reported 53 HIGH verification and 57 HIGH development findings; zero CRITICAL. All 220 exact findings across 15 CVEs are explicitly scoped in the register. Debian Trixie stable/security advisory status was checked on November 27, 2026; supported fixes were not identified for these specific findings. The expiry is December 27, 2026 at 00:00 UTC, earlier than the 30-day ceiling.

- 200 affected-risk decisions are limited to the documented educational images and runtime configuration. Non-root execution, zero capabilities, no-new-privileges, seccomp, removed setuid/setgid bits under `/usr`, empty fstab, and default offline execution mitigate exposure but do not fix vulnerabilities. SQLite FTS5/session, QUIC code and development curl remain present. Do not process untrusted databases, archives or network inputs, or run privileged containers. The optional IDE network overlay and arbitrary reader code increase exposure.
- 20 limited-absence decisions require the same observed absence on each new scan: systemd-homed/homectl at tested locations, Archive::Tar in default Perl search paths, and verification-only infocmp at its standard path/on PATH. These are narrowly scoped observations, not proof of global absence, historical layer removal, or OpenVEX `not_affected` statements. No OpenVEX document is issued.

## Operating procedure

Run `python3 -B containers/assurance/test_security_gate.py` on the host. On each PR and weekly scheduled run, retain all raw artifacts and inspect disposition counts. Review Debian and upstream advisories on each scheduled scan and before release; the scanner database is not a complete substitute for vendor review. If a supported fix is available, revoke the affected acceptance and refresh the pinned snapshot/base through a reviewed change. If no fix exists, reassess exact scope and obtain explicit maintainer renewal before expiry; do not auto-extend dates. Review known-exploited and actionable lower-severity findings separately. Preserve the approval and exact release evidence with the release record. A security PASS is not production certification or proof of reachability. The scanner archives are checked against pinned hashes; independent publisher checksum verification remains a separate provenance limitation unless documented as completed.
